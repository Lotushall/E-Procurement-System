# ประมาณการระยะเวลาโปรเจกต์ E-Procurement System

> จัดทำ: 2026-08-03 (ปรับปรุง 2026-08-03) · ขอบเขต: TOR → ประกาศ/RFQ → เสนอราคา → พิจารณาผล/อนุมัติ → สัญญา → รายงาน/แจ้งเตือน · กำลังคน: 1 คน + AI pair-programming เต็มเวลา
>
> **หมายเหตุขอบเขต:** เวอร์ชันนี้ตัด **ใบสั่งซื้อ (PO)**, **ตรวจรับพัสดุ & เบิกจ่าย**, และ **Hardening** ออกชั่วคราวเพื่อนำเสนอผู้บริหารในรอบนี้ — จะวางแผนเพิ่มเติมภายหลัง ระบบตาม timeline นี้จะยัง**ไม่ครอบคลุมถึงขั้นตอนเบิกจ่ายงบประมาณจริง**

## ⚠️ ข้อสมมติและข้อจำกัดของประมาณการนี้ (อ่านก่อน)

โปรเจกต์นี้**ไม่มีเอกสาร requirement/scope ฉบับเต็มอยู่ในโค้ด** — ที่เจอมีแค่ spec/plan รายฟีเจอร์ใน `backend/docs/superpowers/` (Auth, User, Vendor) และ page stub `frontend/app/dashboard/tor/page.tsx` เท่านั้น ตัวเลขในเอกสารนี้จึงเป็น **top-down sizing estimate** ที่ประเมินจาก:

1. **Velocity จริงที่ทำได้** — 2026-07-04 ถึง 2026-07-31 (~4.3 สัปดาห์) ทำ Auth + User + Vendor module (domain entities, ลงทะเบียน, แก้ไขข้อมูล, เอกสาร, ผู้ติดต่อ, workflow อนุมัติ/ปฏิเสธของแอดมิน พร้อม pagination/filter/search) เสร็จ รวมทั้งสร้าง DDD module generator tooling ไว้ใช้ต่อ (217 commits)
2. **ขนาดสัมพัทธ์** เทียบกับ Vendor module ที่ทำเสร็จแล้ว (ใช้เป็นหน่วยฐาน "1 โมดูลขนาดกลาง ≈ 2.5–3 สัปดาห์")
3. ขอบเขตครอบคลุมถึง**การจัดหาและทำสัญญา**: TOR → ประกาศ/RFQ → เสนอราคา → พิจารณาผล/อนุมัติ → สัญญา → รายงาน/แจ้งเตือน (ยังไม่รวม PO, ตรวจรับ/เบิกจ่าย, Hardening — ดูหมายเหตุด้านบน)

**ความคลาดเคลื่อนที่เป็นไปได้: ±30–40%** สาเหตุหลักคือไม่มี SRS/requirement เป็นลายลักษณ์อักษร โมดูลที่ยังไม่เริ่ม (TOR เป็นต้นไป) จึงมีความไม่แน่นอนสูงกว่า Auth/Vendor ที่ทำเสร็จแล้วมาก แนะนำให้ **re-baseline ตัวเลขนี้ใหม่ทุกครั้งที่จบแต่ละ Phase** โดยเทียบ effort จริงที่ใช้กับที่ประมาณไว้

ไม่ได้รวม: การเจรจา/จัดหา infrastructure จริง (server, domain, ใบรับรอง e-signature), การเชื่อมต่อระบบภายนอก (เช่น GFMIS, ระบบชำระเงิน) หากมี, และงานด้าน compliance ตาม พ.ร.บ. จัดซื้อจัดจ้างภาครัฐที่อาจต้องปรึกษาผู้เชี่ยวชาญด้านกฎหมาย/ระเบียบพัสดุเพิ่มเติม

## ความเสี่ยงหลักที่อาจทำให้ timeline เลื่อน

- **ไม่มี SRS/requirement เป็นทางการ** — ความเสี่ยงอันดับ 1 ที่ทำให้ประมาณการคลาดเคลื่อน โดยเฉพาะ Phase 4, 5 ที่ซับซ้อนและเกี่ยวข้องกับระเบียบพัสดุโดยตรง
- **e-Bidding (Phase 4)** ต้องออกแบบเรื่อง sealed bid, ป้องกันการรู้ราคาคู่แข่งก่อนเปิดซอง, หลักประกัน — งานด้าน security ที่ควรมี code review เพิ่มเติม
- **Evaluation & Award (Phase 5)** เป็น workflow หลายบทบาท/หลายระดับอนุมัติ ต้องตรงกับระเบียบจัดซื้อจัดจ้างจริงของหน่วยงาน ถ้ากติกาเปลี่ยนระหว่างทางจะกระทบมาก
- **ขอบเขตยังไม่ครบวงจรการเงิน** — PO, ตรวจรับ/เบิกจ่าย, และ Hardening ถูกตัดออกจากรอบนี้ (รวม ~8 สัปดาห์) ต้องวางแผนเพิ่มเป็นเฟสถัดไปก่อนใช้งานจริง
- **Solo developer** — ไม่มี parallel work, ถ้าป่วย/ติดธุระ/สลับไปแก้ bug เดิม จะดันทุก phase ถัดไปตรง ๆ
